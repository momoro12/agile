# Стандарты кодирования и практики разработки

**Проект:** Система интеллектуального мониторинга и анализа инцидентов информационной безопасности

---

## 1. Введение

Настоящий документ определяет набор правил, запретов и рекомендаций по написанию исходного кода для модулей системы интеллектуального мониторинга. Соблюдение данных стандартов направлено на повышение безопасности, читаемости, надежности и поддерживаемости программного обеспечения.

Стандарты разработаны на основе материалов **Лекции 10** «Стандарты и хорошие практики кодирования на языках высокого уровня» и адаптированы под специфику проекта в области информационной безопасности.

---

## 2. Стандарты кодирования (C++)

Все правила разделены на три категории:

- **Запреты** — нельзя нарушать ни при каких условиях
- **Требования** — должны выполняться всегда, если не обосновано иное
- **Рекомендации** — желательны к исполнению для улучшения качества кода

---

### 2.1. Запреты

#### 1. Запрещается использовать «магические числа» в исходных текстах

В системе безопасности числовые значения (порты, таймауты, коды ошибок, константы алгоритмов) должны быть именованы. Это исключает ошибки при изменении конфигурации и облегчает аудит кода.

**Неправильно:**

```cpp
if (retryCount > 3) {
    blockIP();
}
double risk = score * 0.85;
```

**Правильно:**

```cpp
const int MAX_RETRY_COUNT = 3;
const double RISK_WEIGHT = 0.85;

if (retryCount > MAX_RETRY_COUNT) {
    blockIP();
}
double risk = score * RISK_WEIGHT;
```

---

#### 2. Запрещается использовать язык, отличный от английского, в комментариях

Исходный код системы может подвергаться аудиту международными специалистами. Кодировки могут не поддерживаться на всех рабочих местах.

**Неправильно:**

```cpp
// Проверка на вирусы
checkViruses();
```

**Правильно:**

```cpp
// Virus check
checkViruses();
```

---

#### 3. Запрещается размещать более одного оператора на одной строке

Это усложняет чтение и отладку критических участков кода обработки инцидентов.

**Неправильно:**

```cpp
alertLevel++; sendLog(); if (alertLevel > 5) notifyAdmin();
```

**Правильно:**

```cpp
alertLevel++;
sendLog();

if (alertLevel > 5) {
    notifyAdmin();
}
```

---

### 2.2. Требования

#### 1. Необходимо инициализировать локальные переменные перед их использованием

В системе мониторинга неинициализированная переменная может привести к утечке данных или ложному срабатыванию защиты.

**Неправильно:**

```cpp
int threatLevel;
// ... какой-то код ...
if (threatLevel == CRITICAL) { ... }
```

**Правильно:**

```cpp
int threatLevel = LEVEL_NONE;
// ... какой-то код ...
if (threatLevel == CRITICAL) { ... }
```

---

#### 2. В объявлении функции или метода обязательно должны присутствовать имена аргументов

Это повышает понятность интерфейсов системы для других разработчиков.

**Неправильно:**

```cpp
void addLog(int, std::string, bool);
```

**Правильно:**

```cpp
void addLog(int errorCode, std::string message, bool isCritical);
```

---

#### 3. Все глобальные переменные и константы должны быть определены в одном месте

Для конфигурации системы безопасности следует использовать отдельные файлы (например, `security_config.h` и `security_config.cpp`), чтобы избежать конфликтов имен.

> **Требование:** Объявление в `.h` (с `extern`), определение в `.cpp`.

---

### 2.3. Рекомендации

#### 1. Рекомендуется при проверке условий ставить константу на первое место (Yoda conditions)

Это предотвращает случайное использование оператора присваивания `=` вместо сравнения `==` в критических проверках доступа.

**Рекомендуется:**

```cpp
if (TRUE == isAuthorized) { ... }
// или
if (0 == errorCode) { ... }
```

**Не рекомендуется:**

```cpp
if (isAuthorized == TRUE) { ... } // Риск написать = вместо ==
```

---

#### 2. Рекомендуется, чтобы все имена классов начинались с большой буквы (CamelCase)

Единый стиль именования упрощает навигацию по коду системы.

**Пример:**

```cpp
class SecurityEventAnalyzer;
class IncidentDatabase;
```

---

#### 3. Рекомендуется избегать использования оператора `goto`

Для обработки ошибок в модулях мониторинга следует использовать исключения или код возврата, чтобы не нарушать структуру потока выполнения.

> **Исключение:** Допустимо только для выхода из глубоко вложенных циклов при критической ошибке, если это упрощает код.

---

## 3. Чек-лист для проверки корректности кода (Code Review Checklist)

Перед выставлением кода на инспекцию автор обязан проверить следующие пункты:

| № | Пункт проверки | Описание |
|---|----------------|----------|
| 1 | **Отсутствие магических чисел** | Все числовые константы вынесены в `const` переменные или `enum`. |
| 2 | **Инициализация** | Все локальные переменные инициализированы при объявлении или перед первым использованием. |
| 3 | **Язык комментариев** | Все комментарии в коде написаны на английском языке. |
| 4 | **Имена аргументов** | В объявлениях функций указаны имена параметров, а не только типы. |
| 5 | **Длина строки** | Длина строк исходного кода не превышает 100 символов. |
| 6 | **Стиль именования** | Имена классов начинаются с заглавной буквы, макросы — полностью заглавные (`UPPERCASE`). |
| 7 | **Безопасные сравнения** | В условиях сравнения константы стоят слева (например, `if (NULL == ptr)`). |
| 8 | **Отсутствие `goto`** | Оператор `goto` не используется (за исключением обоснованных случаев обработки ошибок). |
| 9 | **Оформление блоков** | Фигурные скобки `{ }` расставлены единообразно (либо друг под другом, либо с наложением). |
| 10 | **Заголовки** | Каждый файл и каждая функция имеют заголовок в виде комментария установленного образца. |
